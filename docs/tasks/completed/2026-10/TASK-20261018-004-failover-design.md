当前服务商优先级只解决**发送前根据配置选目标**，并不解决 429／余额不足／上游拒绝后的自动切换。完整健康／负载调度也尚未实现。

### 方案取舍

- **采用：应用层有界账号切换＋按尝试记账＋短期运行状态。** 复用既有路由、凭据和适配器，无新增大型依赖。
- 在提供商适配器内直接循环账号：无法统一固定规则、凭据边界及统计，拒绝采用。
- 直接围绕 Forward 加重试循环：缺少错误阶段、候选范围和记账支持，容易重复请求／污染用量，拒绝采用。
- 一次实现负载均衡、动态权重、跨服务商熔断和全自动额度预测：超出当前需求，后续确有需求再单独设计。

### 建议的首版行为

1. 沿用当前配置解析，确定初始服务商和计费通道，随后冻结本次请求的服务商配置 ID、认证类型、计费模式与地区／集群；不同配置即使 Kind 同名也不混用。不会把订阅账号切到 API Key／按量账号。
2. 同池候选仍须启用、具备该模型／协议能力及适用上下文限制。每次真正调用前重新检查状态、凭据／通道版本，沿用 UseAPIKeyAt 等保护；配置变更不得扩展原候选池。
3. 建议保留用户显式固定账号的强制语义：只使用该账号，失败明确返回。系统生成的兼容别名不能仅凭 Matched 或 AccountID 非空就误判为用户手工固定，需要保留规则来源。
4. 候选沿用已有创建时间／ID 稳定顺序，每个账号每次逻辑请求最多尝试一次；建议总共最多 3 次（首次＋最多两次切换），沿用整个请求现有的 120 秒总期限，不在每次尝试时重置 deadline。
5. 不在同一请求内等待长冷却；有同池健康候选就选下一个，否则快速返回最后的具体失败或明确的池不可用及适用 Retry-After，不继续切服务商或计费通道。
6. **保守的成功边界：上游 200 一旦被当前尝试接受，就不再自动重放。** 首版只处理成功响应之前的明确拒绝／确认未发送失败；不会因为 200 后解析错误、断流、尚未出字或尚未写客户端而重新生成。HTTP 任何响应已提交、WebSocket 任何本次响应事件已发送时同样禁止切换。
7. 首版不为“首字超时”新增更短的超时，也不缓冲正常流式首事件来等待重试；保持当前 SSE 延迟与资源上限。

是否默认启用、最大尝试数是否开放设置、无 Retry-After 的默认冷却值：**TBD，建议实施时定稿**；本记录中的 3 次等数值是建议。

### 错误处理矩阵（建议）

| 情况 | 本次请求是否尝试下一个账号 | 运行状态处理 |
| --- | --- | --- |
| 明确的上游 429／配额窗口耗尽 | 只有已确认是可切换的账号配额且未成功响应时才切换 | 按 Retry-After／已知重置时间冷却对应配额范围 |
| 明确的上游 401、提供商确认的余额不足／账号失效 | 可在同池尝试其他账号；复用既有授权刷新，不额外循环刷新 | 单独标记运行异常，不擅自修改用户启用开关；凭据更新／显式重试可解除 |
| 上游 403 | 默认直接返回；只有适配器明确识别的账号权限拒绝才考虑跳过 | 不将所有 403 当作密钥失效，不绕过服务端限制 |
| 适配器明确识别的服务繁忙／拒绝执行，如已核对的 overloaded 响应 | 在提供商契约支持、未成功响应且未产生结果时可有界尝试；不能泛化为所有 5xx | 识别账号级和服务商级影响，服务商整体故障不遍历所有账号 |
| 拨号等明确发生在发送前的连接失败 | 可以尝试下一候选；无法确定请求是否发送则不重试 | 传输阶段用结构化状态表示，未知按可能已发送处理 |
| 请求已发送后的读超时、连接断开，泛化 500／502／504 或未知错误 | 首版直接返回，不据“客户端还没出字”猜测上游未执行 | 可记录后续健康观察，不自动重放当前请求 |
| 参数／模型／上下文不兼容、客户端断开、主动取消、总超时、本地并发满、记账／配置错误 | 不切换 | 保留原错误和取消行为，不把本地 429／503 当上游故障 |
| 上游 200 后的任何解析／流式错误、下游写入失败 | 不切换 | 结束／中断本次响应，保留已知用量与实际失败状态 |

错误分类由适配器依据状态与有界结构化字段产生，禁止记录原始错误正文、密钥、账号名称前缀或请求内容。401／402 等同样不能脱离提供商契约一概解释；流内错误不能套用 HTTP 状态表。

### 冷却与并发

- 首版建议使用有界内存运行状态，支持到期清理；应用重启后重新观察，不主动发模型探测请求，不将未知官方额度推断为可用或耗尽。
- 冷却键包含公开账号 ID、凭据／配置版本、必要的模型或额度组；429 只影响对应窗口，不误伤该账号全部模型。适配器应识别已知共享项目／工作区的限额，多个 Key 不等于多份额度，不能用换 Key 规避项目级限制。
- Retry-After 接受规范定义的秒数和 HTTP-date，并做长度、时间范围、溢出及过去日期校验；无有效值时的短冷却常量待定。
- 到期后只允许一个正常业务请求先行尝试恢复，其他并发请求可用同池健康账号；锁仅保护状态与资格，不跨网络持锁。成功清除对应失败状态，释放恢复资格的路径必须覆盖取消与异常。
- 保留现有网关并发上限；首版不增加自动并发扩容、账号权重或后台健康流量。已在途请求不能被后来的冷却记录反向换目标。

### 尝试级记账与界面

- 保留一个客户端 request_id 和一条逻辑请求结果；增加以 `(request_id, attempt_index)` 唯一识别的尝试明细，保存目标快照、开始／结束时间、稳定错误分类、状态与上游报告的用量，不保存正文、凭据引用或请求头。
- 每次尝试有独立用量快照，不能将 A 的用量带到 B、不能用 max 代替跨尝试求和。父记录汇总已知值并保留完整性标记；未报告的用量保持未知，不能伪造为零。
- 全局请求数、最终成功率和总耗时仍按一次客户端请求统计；尝试数单独展示。建议原账号请求数归最终服务账号，其他失败尝试通过新增尝试字段展示；账号／模型 Token 累计始终按实际报告账号归属，兼容性要用契约测试明确，不能悄悄把既有请求数改成尝试数。
- 新迁移编号在实施时分配；旧记录作为历史单次请求兼容，不能虚构历史尝试。尝试明细随父明细一起淘汰，累计保持独立；幂等提交、重复完成、崩溃恢复和未完成尝试也需覆盖。
- 网关／请求详情可显示“切换 1 次后成功”以及 A 账号限流→B 成功的尝试过程；运行冷却／认证异常单独显示，不覆盖用户启用状态。目录与配置预览仍以配置资格为准，不因临时冷却从模型列表消失。

### 实施位置和顺序

1. **路由计划与纯策略**：从当前 evaluate 提取共用候选逻辑，增加请求级计划，保留固定规则来源和池身份。Core 只处理候选／错误策略等中立类型，不依赖数据库、Wails 或 React。
2. **统计基础**：增加尝试事件、追加迁移及 activity 事务，先让单次请求通过新模型且兼容旧统计，再允许第二次尝试。
3. **协调与错误适配**：在 application/gateway 中执行有界顺序尝试，适配器返回安全的拒绝／发送阶段信息。当前调用完全结束、响应关闭和凭据回调退出后，才开始下一次；不把 io.Reader 带出有效回调。
4. **分批验收**：先以 DeepSeek 和 ChatGPT／Codex 两条成熟链路完成 HTTP／SSE／WebSocket 的明确拒绝场景，再逐个提供商核对结构化错误、共享额度与通道限制。未核实的提供商错误不自动重试。
5. **最小界面与文档**：补切换开关、运行状态及尝试详情，明确成功响应后的错误仍交由客户端处理。实施时新增／修订 ADR 并同步 PRD、GATEWAY、ACTIVITY 与相关计费 ADR；本分析不提前改变 Accepted 决策。

建议流程：`解析并冻结账号池 → 排除本次已试及冷却目标 → 登记尝试 → 重新校验并发送 → 成功响应则进入现有消费流程；明确可切换拒绝则结束尝试并释放资源 → 更新冷却 → 有剩余预算才选下一账号 → 完成一次逻辑请求`。

### 必须验证的行为

- A 返回已识别 429、B 成功：只有一个客户端响应、一次逻辑请求，尝试为两次，目标与用量归属正确；A 在冷却期内不被后续请求再次选中。
- 固定 A、订阅 A、国内／海外／集群 A：不能换到未授权的账号、服务商、计费方式或地区；兼容别名和首选计费规则保持正确。
- 第一个候选后续被停用、删除、换 Key 或改通道：读取版本拒绝旧目标，不能误发旧凭据或跨通道补位。
- 200 后首个 SSE 心跳／创建事件／正文／工具片段、流内错误、JSON 解析失败、WebSocket response.created 后断流：均不出现第二次上游生成；不会拼接两次响应 ID／工具调用。
- 本地鉴权／并发／记账失败、客户端取消、总超时：不重试；与明确发送前失败、上游配额拒绝区分。
- 所有候选冷却或失败、同一账号的重复配置、非法／超大 Retry-After、共享项目额度、并发恢复探测：有限次数、无忙等、状态范围正确。
- 尝试事件重复投递、部分用量后失败、历史迁移、父子保留上限与崩溃恢复：累计不重扣／不漏记，不把未知写成零，明细淘汰不减少累计。
- 客户端自身重试与网关尝试叠加时仍有单次上限；内部 request_id 不能当作上游跨账号幂等保证。
- 使用 httptest／可控 RoundTripper、临时 SQLite 和可注入时钟；功能实施后运行定向契约／集成、原生详情验收及完整 task verify。真实账号小额回归应单独记录实际范围。

### 外部依据与限制

- [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)：POST 不天然幂等，不能从未收到输出推断上游未执行；本方案不做通用透明 POST 重放，切换需有应用级拒绝语义／未发送证据。
- [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)：Retry-After 有秒数和 HTTP-date 两种形式。
- [DeepSeek 官方错误码](https://api-docs.deepseek.com/quick_start/error_codes/)：429 为速率／并发限制，503 为服务过载；文档允许部分服务器错误稍后重试，但不代表任意中断均未执行或换账号一定有效。
- [Claude 官方错误说明](https://platform.claude.com/docs/en/api/errors)：SSE 可在 HTTP 200 后报错，不能仅按状态码判定成功或重新生成。此处作为流式协议风险依据，不代表 OmniProxy 已完成 Anthropic 适配。

上述自动尝试策略是结合代码提出的建议；不承诺跨账号 exactly-once 或故障期间零额外计算。首版限制到明确拒绝／未发送场景，可减少执行结果不确定时的重复消费。
