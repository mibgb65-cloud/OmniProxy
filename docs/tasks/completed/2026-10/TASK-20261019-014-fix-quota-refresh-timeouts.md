# Analysis

## Root Cause

- 1.0 通过独立 HTTP Validator 查询固定 `wham/usage` 端点，使用 12 秒 HTTP 超时；按需续期与查询、激活为分开的调用。
- 2.0 `UseTokenAt` 在持有 `Service.operations` 全局互斥锁时执行整个凭据消费回调。网关 HTTP／WebSocket 流及自动激活网络请求都在回调内，因此长响应阻塞所有账号的额度查询、授权管理与自动激活。
- `ReadQuota` 使用不可取消的 `sync.Mutex.Lock`，自身 30 秒预算在取得锁后才启动；Wails 的 30 秒上下文可能已在排队中耗尽，甚至不能及时返回。排队失败与网络超时目前使用同一提示。
- 既有 001／006／010 任务已覆盖窗口判定、故障转移、续期及诊断，除经官方协议核实需纠正的无条件强刷外，不重复改写这些行为。历史真实故障的唯一原因不能仅凭代码推定，本次修复确定的阻塞缺陷及多余认证往返。
- 继续只读检查生产日志，最近 10 条额度失败分别发生于 queue 1 次、open 2 次、refresh 7 次，不能把全部超时归因于排队。
- 官方当前 app-server 文档明确：managed ChatGPT 模式下 `account/read(refreshToken=true)` **强制**刷新令牌；与本机已导出的 `GetAccountParams`「proactive token refresh」协议一致。010 将每次额度查询前强制刷新误当作按需续期，额外认证往返可能先耗尽查询预算。官方组件本身负责托管授权的自动续期；正常额度读取无需主动强刷。依据：[官方 app-server 授权说明](https://learn.chatgpt.com/docs/app-server)。

## Decision

不照搬旧版自行管理 OAuth 的实现、不改变现有凭据存储或引入独立令牌缓存，不增加应用层重试与延长超时。额度查询先读取托管身份（refreshToken=false），再让官方组件读取额度和管理正常授权；手动刷新状态与网关原有取令牌前续期不变。保留官方组件、隔离凭据、身份版本校验、串行准备及持久激活去重；只在锁内完成续期与令牌短期副本读取，网络消费在锁外执行，回调结束即清零副本。操作排队改为可取消，总查询预算包含排队，排队超时使用独立安全提示。

# Implementation Result

## Changes

- 额度查询不再无条件执行 `account/read(refreshToken=true)`，改为核验托管身份后正常读取官方额度；不跳过成员邮箱及工作区校验，不改变授权状态或清空最后成功快照。
- 网关及自动激活的取令牌路径只在全局锁内完成凭据准备，准备锁在模型网络消费回调之前释放。短期 Token 副本只用于本次回调，成功、失败或 panic 退出后均清零；准备失败和取消不进入消费，不增加令牌缓存或日志。官方授权／额度操作仍串行。
- 不可取消的互斥等待替换为零值可用的上下文门闩；额度 30 秒总预算从排队前开始，其他授权操作及登录完成保存也响应其已有上下文。
- 增加 quota_busy 稳定错误码与中英文提示，排队超时不再误报为网络故障；实际请求超时仍保留 quota_timeout，旧版 quota_refresh_failed 映射保持兼容。
- 自动激活的窗口判定、官方模型选择、发送前复查、持久去重和结果不确定不重发原则均不变，本次同时改善它复用的额度／凭据路径。
