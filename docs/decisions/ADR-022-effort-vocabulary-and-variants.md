# ADR 022: 推理档位按客户端词汇发布，变体型号由网关折叠

Status: Accepted

Date: 2026-10-24

## 背景

Codex 目录（`omniproxy-models.json`）只接受 official catalog 的推理档位词汇；上游用
`none`／`max` 表达两端，Codex 不认识这两个值，选择器只显示唯一一个已认识的值
（实测 `DeepSeek-V4.1-Flash-1017` 只能停在「高」，无法切换）。

Google 系上游用**独立型号**表达 thinking level（`…-low`、`…-high`，显示名 `Gemini 3.8 Flash (Low)`）。
目录照搬后客户端看到的是多个"模型"：同一型号出现多行、档位变成模型名，
而且 `reasoning_effort` 会被订阅适配器的生成参数白名单拒绝。

## 决策

- 目录向客户端发布的档位必须是客户端自己的词汇：Codex 用 `minimal`／`low`／`medium`／
  `high`／`xhigh`／`ultra`，上游 `none → low`、`max → xhigh` 就近映射，其余档位原样
  （official catalog 为 GPT-6 系声明的 `ultra` 必须原样发布，不能当未知值丢弃）；
  未确认的档位不发布。
- 网关接收请求时按同一套映射还原上游取值（`low → none`、`xhigh → max`），
  只接受该模型已确认的枚举，未确认时返回 `unsupported_request_effort` 类安全错误码。
- 上游用独立型号表达档位时，目录把它折叠回基础模型：只发布一行，
  `Metadata.EffortModels` 记录档位 → 变体 ID 的映射（不发给客户端）。
  请求期把客户端档位换成实际存在的变体 ID，并移除已表达的档位字段，
  避免适配器收到不认识的参数。
- 折叠只在同名基础模型同时存在时发生；只有变体的孤立型号保持原样。
  历史保存的变体 ID 通过反向映射还原成「基础模型 + 档位」，不会变成未知模型。
- `Metadata.EffortModels` 属于目录内部数据，`/v1/models` 与 Codex 目录都不输出。

## 后果

- Codex 与 Claude 系客户端选择档位时看到的是自己认识的取值，不再出现"只能选一个"。
- Google 系型号在客户端只占一行；档位由客户端 effort 控件选择，网关负责换型号。
- 上游新增档位变体时，只有同时发布基础模型才会折叠；命名不符合 `(High)`／`(Low)`／
  `(Medium)`／`(Minimal)`／`(Ultra)` 约定的变体保持独立条目。
- 折叠在下次同步模型时生效；已保存的旧变体 ID 仍可解析，但目录刷新后菜单会少掉那些行。
- 档位映射是就近语义（`none` → `low`、`max` → `xhigh`），不等于上游关闭思考／最高强度
  在客户端有同名选项；描述文案沿用上游，不夸大能力。official catalog 声明的 `ultra`
  不需要映射，原样发布与还原。

## 2026-11-18 补充：变体解析必须在选服务商之前

折叠只在基础模型同时存在时发生，因此“只有变体、没有基础模型”的型号（Gemini 4 的
`…-high／-low／-medium`）会作为独立条目发布。一旦**另一个**服务商（例如中转站）发布了
同前缀的裸型号，路由就会精确命中那个裸型号，官方订阅的档位变体永远进不了候选——
桌面端按自带注册表发送的正是“家族名 + 档位”，于是官方订阅一直收不到这类请求。

现在把变体解析提前到选服务商之前：

- 只对客户端**明确给出档位**（Chat `reasoning_effort`、Responses `reasoning.effort`、
  Messages `output_config.effort`）的请求生效；没有档位不猜，保持精确匹配。
- 同族必须确认**至少两个**档位后缀，才把后缀当档位；单个后缀可能只是型号名的一部分。
- 只接受**精确档位**匹配，不做就近替换（`high` 请求不会悄悄降成 `medium`）。
- 改写后按变体的服务商路由；找不到对应变体时完全不改写。

后果：Gemini 3.8／4 家族的“家族名 + 档位”请求改由官方订阅承接（例如
`gemini-4-carbon` + `high` → `gemini-4-carbon-high` → Google 账号），中转站的裸型号只在
客户端未给档位时才会被选中。官方订阅池全部冷却时这类请求按池冷却返回 429，不再
静默切到中转站——用哪家额度是用户的明确选择，不由目录顺序决定。相关任务：
TASK-20261118-008。
