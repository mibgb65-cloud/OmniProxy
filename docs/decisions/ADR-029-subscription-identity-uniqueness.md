# ADR 029: 订阅账号身份唯一，重新登录复用原账号记录

## Status

Accepted

## Date

2026-11-20

## Context

Google／Antigravity 与 ChatGPT／Codex 两条订阅登录路径都以「是否携带本地 accountId」决定保存方式：
携带时更新该账号，未携带时直接 `INSERT INTO accounts`。账号页的「添加账号」不携带 accountId，
因此用户退出登录后再次添加同一个官方账号，会在账号表里留下两条身份完全相同的记录。

同一条身份出现两次会带来实际影响：`account_catalog_versions` 是
`credential_ref || ':' || auth_account_id` 的视图，两次授权各自持有一份目录与额度快照，
网关把同一个上游账号当成两个候选账号参与轮换与故障切换，额度、冷却和「按账号」统计的归属也随之分裂。
本机生产库中已实测到一对这样的记录（同一 `auth_email`、同一 `auth_account_id`，
一条 `logged_out`、一条 `authenticated`）。

订阅身份的比较口径在 `docs/product/ACTIVITY.md` 已经存在：提供商类型 + 规范化邮箱 + `account_id`。
同一 Team 工作区中邮箱不同的成员是不同账号，因此邮箱必须参与身份，不能只按 `account_id` 判重。

## Decision

- 订阅身份 = 提供商 + 规范化邮箱（小写、去空白）+ 官方 `account_id`；同一身份在账号表中只保留一条记录。
- 两条订阅登录路径在**新建账号前**先按身份查询已有记录：命中就更新该记录（`id`、`name`、`enabled`、`created_at` 保持，
  凭据、`auth_state`、`auth_plan`、`auth_email` 更新为新授权），未命中才新增。
- 双方 `account_id` 都存在且不同时不合并（同工作区不同成员、不同工作区仍各自成账号）；
  旧记录缺少 `account_id` 时按同提供商同邮箱认领，并由这次登录补全该字段。
- 邮箱或 `account_id` 缺失（身份不完整）时不做合并，保持原有保存行为，避免把未知身份写到已有账号上。
- 重新登录沿用既有语义：旧授权版本的目录与额度快照不重绑定（只清理凭据），不恢复旧快照。
- 不在登录过程中自动删除已存在的重复账号：历史账号行、目录与额度快照属于用户数据，
  由用户在账号页手动删除。（用量累计按身份保存在 `usage_accounts.subject`，删除重复卡片不减少累计。）

## Alternatives Considered

- **数据库唯一索引（provider + lower(auth_email) + auth_account_id）**：最能保证不变量，
  但既有数据库里已经存在重复行，迁移必须先删数据；且无法表达「旧记录缺少 account_id」的过渡状态，否决。
- **登录时自动合并／删除重复账号**：能立即消掉已有重复卡片，但属于未经确认的删除用户数据，且需要处理
  目录、额度快照与请求明细的归属，风险与收益不成比例，否决。
- **只在前端禁止对已有账号再点「添加账号」**：前端无法在授权完成前知道身份，重复仍会在后端产生，否决。
- **只按 account_id 判重**：会把同一 Team 工作区里不同邮箱的成员合并成一条，否决。

## Reasoning

身份判重必须发生在授权完成、拿到官方身份之后，也就是后端保存路径上；这既是唯一能拿到 `email` 与
`account_id` 的时机，也覆盖前端所有入口（添加账号、卡片重新登录、事件恢复）。按身份判重与既有的
「统计身份」口径一致，不需要引入新的业务概念。

## Consequences

- 「添加账号」重复授权同一账号时，结果是更新原账号并返回它，账号数量不再增长；
  登录弹窗里填写的名称在复用路径下被忽略（保留原名称）。
- 已有重复记录不会被自动清理：升级后需要用户手动删除多余的卡片（删除会同时清理该行自己的目录与额度快照）。
- 身份不完整的登录（例如读取 `account_id` 失败）仍可能新增记录；这类账号需要先「刷新状态」补全身份。
- 不新增数据库迁移；数据库层面不强制唯一，不变量由应用层在两条订阅登录路径上维护。
