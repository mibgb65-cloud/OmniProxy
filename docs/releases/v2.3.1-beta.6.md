# OmniProxy v2.3.1-beta.6

## Bug Fixes / 问题修复

- After v2.3.1-beta.5 the Codex entry routes non-OpenAI models correctly, but a Codex Desktop turn on `deepseek-ai/DeepSeek-V4.1-Flash-1017` still showed six failed requests (`18:47:25–18:47:36`) with `upstream_stream_failed`, zero tokens and a client-side `stream disconnected before completion: network error: error decoding response body`. The gateway could not say whether the upstream had reported an error or the stream had simply been cut off, because both cases collapsed into one error code with no diagnostic field. / `v2.3.1-beta.5` 之后 Codex 入口已能正确路由非 OpenAI 模型，但 Codex 桌面端一次 `deepseek-ai/DeepSeek-V4.1-Flash-1017` 会话仍有 6 条 `upstream_stream_failed`（18:47:25–18:47:36、0 Token），客户端只显示 `stream disconnected before completion: network error: error decoding response body`。网关无法区分「上游主动报错」与「流被截断」，因为两者共用一个错误码，日志里也没有可核实的字段。
- The protocol path now classifies each SSE data line on its own evidence: an upstream-reported error (non-null `error`, or a non-null `response.error`) becomes `upstream_error_event`, while malformed JSON or valid JSON that is not an object keeps `upstream_stream_failed`. `gateway request finished` additionally logs `upstream_stream_kind` (`upstream_error` / `invalid_json` / `unexpected_shape`), `upstream_event_type` and `upstream_error_code`, the latter two reduced to printable short codes of at most 40 characters. Upstream message text is still neither echoed to the client nor written to logs. / 协议路径现在按可核实证据逐行分类：上游主动报错（`error` 非空，或 `response.error` 非空）记为 `upstream_error_event`；非法 JSON，或合法但不是 JSON 对象，仍记为 `upstream_stream_failed`。`gateway request finished` 另外记录 `upstream_stream_kind`（`upstream_error` / `invalid_json` / `unexpected_shape`）、`upstream_event_type` 与 `upstream_error_code`，后两者压成最长 40 字符的可打印短码。上游说明文字仍然既不回显客户端，也不写日志。
- Investigation note for this failure window, verified against the running beta.5: the captured 103 372-byte body of an equivalent Codex turn (8 `namespace` plus 11 `function` tools, `store: false`, `include`, `prompt_cache_key`, full `client_metadata`) completed 18 out of 18 sequential replays, a real `codex-cli 0.163.0` turn with the production `CODEX_HOME` answered normally, and Desktop-only fields (`personality`, `reasoning.summary`, `text.verbosity`, `service_tier`, `truncation`, `instructions`) were all accepted. Payload shape and routing are therefore not the trigger; the window itself was an upstream-side failure, and routing is unchanged in this release. / 失败窗口的调查结论（均在运行中的 beta.5 上验证）：与桌面端等价的一份 103 372 字节正文（8 个 `namespace` 加 11 个 `function` 工具、`store: false`、`include`、`prompt_cache_key`、完整 `client_metadata`）顺序重放 18 次全部完成；用生产 `CODEX_HOME` 跑真实 `codex-cli 0.163.0` 一轮对话正常；桌面端独有字段（`personality`、`reasoning.summary`、`text.verbosity`、`service_tier`、`truncation`、`instructions`）逐个探测全部通过。因此触发点不是正文形状或路由，该 11 秒窗口属于上游侧失败，本版本不改动路由。

## Breaking Changes / 不兼容变更

None / 无。No database migration, no public API change. One additional stable error code (`upstream_error_event`) can appear in request details; HTTP status stays 502 and the response body still carries only a stable code and the built-in safe message. / 无数据库迁移、无公共 API 变更。请求明细里可能多一个稳定错误码 `upstream_error_event`；HTTP 状态仍是 502，响应正文仍只有稳定错误码与内置安全说明。

## Local update / 本地更新

- Local Windows amd64 Beta installer, not a public release and not signed. Fully exit OmniProxy from the system tray, back up the data directory, then run the installer over the existing installation. / 本版本为本地 Windows amd64 Beta 生产安装包，未公开发布、未签名。请先从托盘完全退出 OmniProxy，备份数据目录，再运行安装器覆盖现有安装。
- Application/frontend version: `2.3.1-beta.6`; Windows numeric resources: `2.3.1.0`; NSIS installer base version: `2.3.1`. / 应用／前端版本为 `2.3.1-beta.6`，Windows 数字资源版本为 `2.3.1.0`，NSIS 安装器基础版本为 `2.3.1`。
- Existing accounts, routes, statistics and client configuration are preserved; this release has no database migration. / 保留现有账号、路由、统计与客户端配置；本版本没有数据库迁移。

## Verification boundary / 验证边界

- `task verify` passed before packaging: all Go packages, frontend tests, format, lint, typecheck and the Windows production build. / 打包前 `task verify` 通过：Go 全包、前端测试、格式、lint、类型检查与 Windows 生产构建。
- New coverage: table-driven classification for `inspectStreamData` (upstream error event, string error, invalid JSON, non-object shapes), signature sanitisation bounds, `Trace` diagnostic fields, and a gateway end-to-end case asserting a streamed `response.failed` is recorded as `upstream_error_event` with a single attempt and without the upstream message reaching the client. / 新增覆盖：`inspectStreamData` 的表驱动分类（上游错误事件、字符串错误、非法 JSON、非对象形状）、短码净化边界、`Trace` 诊断字段，以及网关端到端用例断言流式 `response.failed` 记为 `upstream_error_event`、只尝试一次且上游说明文字不外泄。
- The upstream failure that produced the original six records was not reproducible afterwards, so this release does not claim to fix it; it makes the next occurrence identifiable from the request list and the log. / 产生那 6 条记录的上游失败事后无法复现，本版本不声称修复它，只让下一次发生时可以从请求明细与日志判断原因。
