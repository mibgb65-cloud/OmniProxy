# OmniProxy v2.0.0-beta.23

本版为 Windows amd64 production 本地 Beta 安装包，供用户手动覆盖更新，未公开发布。

## 本地 Agent 客户端接入图片

- 修正 DeepSeek Harness、OpenCode、Pi、Goose 接入 OmniProxy 时看不到模型图片能力的问题。此前这四个客户端的模型目录被写死为纯文本，客户端据此在本地就拦住了附图，即使上游模型（如 River 的 DeepSeek-V4.1-Flash 系列）本身支持图片。
- 现在按上游**已确认**的能力声明：Harness Web／Desktop 与 Pi 写 `input: [text, image]`，OpenCode 及 Kilo／Qwen／MiMo Code 写 `modalities.input`，Goose 写 `supports_vision: true`。
- 未确认图片能力的模型继续保持纯文本，不会因为同目录其他模型支持图片而放宽。
- 说明：pi-ai 的 `input` 一旦显式非空就优先于安装目录，省略会回落到路由默认值 `[text]`，所以写死纯文本比不写更糟。本版改为如实输出。
- 目录声明只表示「允许客户端发送」；模型能否真正识别由上游决定，`system`／`assistant` 消息中的图片仍按各官方限制由上游拒绝。

## River 图片输入（承接 Beta.22）

- 继承 Beta.22 的 River 图片转发：Messages 的 `image` 块、Responses 的 `input_image`、工具结果中的截图都会转成 Chat `image_url` 发给上游。
- Beta.22 打包时尚未包含本版的客户端目录修复，因此只更新到 Beta.22 时，Harness 等客户端仍看不到图片能力——请直接使用本版。

## 兼容与已知边界

- 继承 Beta.22 及此前各版功能，不新增数据库迁移。
- 不改变安装身份、凭据格式、账号启用状态、路由选择或客户端登录。
- 图片按官方限制只应出现在 `user` 消息中。
- 本版未使用真实 River Key 做图片计费实测，也未在真实 Harness／OpenCode／Pi／Goose 会话中验证发图与识别效果；相关结论由用户本地验收。
- 音频与文件（Files API）输入仍未接入。
- Codex 在约 500k 用量时提前压缩的现象**仍未定位根因**，不宣称已修复，也不修改用户的 1.05M／900k 设置。
- Google 上游 `429 / RESOURCE_EXHAUSTED` 仍是独立调查项。

## 升级后需要做的三步

1. 路由页对 River 账号点一次「同步官方模型」，刷新模型能力元数据。
2. 在应用中重新应用 **Claude Code** 与 **DeepSeek Harness／OpenCode／Pi／Goose** 各自的配置，让客户端目录读到新的图片能力。
3. 完全退出并重新启动对应客户端（Harness 若启用 HMR 则在下一请求生效）。

只做第 1 步不够：客户端配置里保存的是旧目录。

## 安装与数据保留

先从托盘完全退出旧版，再为整个数据目录保留一致性备份，随后运行本安装包覆盖原安装目录，无需先卸载旧版或删除账号数据。安装后在“设置与关于”核对版本为 2.0.0-beta.23。

本版沿用现有安装目录、账号、数据库、设置、请求历史与累计统计，不主动清空数据。不要同时启动新旧版本写入同一数据目录。

本地安装包未签名，Windows 可能提示未知发布者，机器级安装需要管理员确认。构建过程不自动安装、停止或替换生产应用，不上传公开发布；真实覆盖安装与数据保留由用户本地验收。
