# OmniProxy v2.3.1-beta.5

## Bug Fixes / 问题修复

- Codex still failed on non-OpenAI models after v2.3.1-beta.4: the request was routed correctly (River, official model ID) but the gateway rejected it locally within 45 ms with `400 unsupported_content`, so nothing reached the upstream. The real client body — captured with a temporary `CODEX_HOME` and a shape-only listener, using the same ChatGPT login and configuration — carries eight `type: "function"` tools **plus eight `type: "namespace"` groups** (`multi_agent_v1`, `mcp__codex_apps__*`, each holding nested function tools). Codex believes it is talking to OpenAI, which is the only reason it groups MCP and multi-agent tools that way; River accepts function tools only, so its validation rejected the whole request. / `v2.3.1-beta.4` 之后 Codex 选择非 OpenAI 模型仍然失败：路由已经正确（River、官方模型 ID），但网关在 45 ms 内本地判 `400 unsupported_content`，请求没有到达上游。用临时 `CODEX_HOME` 加只记录字段形状的监听器、沿用同一份 ChatGPT 登录与配置，拿到真实正文：8 个 `type: "function"` 工具**外加 8 个 `type: "namespace"` 分组**（`multi_agent_v1`、`mcp__codex_apps__*`，内部是嵌套的函数工具）。Codex 以为自己在跟 OpenAI 说话，才会这样给 MCP 与多智能体工具分组；River 只接受函数工具，于是整条请求被本地校验拒绝。
- When the Codex entry hands a request to a provider other than OpenAI, the gateway now drops those `type: "namespace"` groups after routing, keeps every function tool and every other field untouched, and logs `codex namespace tools dropped` with the count. The removed item is the grouping itself, not user messages, history or function tools; the trade-off is that MCP and multi-agent tools are unavailable on that model while `exec_command`, `read_file`, `view_image` and the other function tools keep working. Probes against the running build confirmed the exact trigger: minimal body, `store: false`, function tools, `include`, `prompt_cache_key`, `service_tier` and `tool_choice` are all accepted, while `store: true`, a non-null `context_management` and namespace tools are rejected — the real client body contains only the last one. / Codex 入口把请求交给 OpenAI 以外的服务商时，网关现在在路由完成后移除这些 `type: "namespace"` 分组，函数工具与其它字段一律保留，并记录 `codex namespace tools dropped` 与数量。移除的是分组本身，不是用户消息、历史或函数工具；代价是该模型上无法调用 MCP／多智能体工具，而 `exec_command`、`read_file`、`view_image` 等函数工具照常可用。对运行中构建的逐项探测确认了唯一触发点：最小正文、`store: false`、函数工具、`include`、`prompt_cache_key`、`service_tier`、`tool_choice` 都被接受，而 `store: true`、非空 `context_management` 与命名空间工具会被拒绝——真实正文只命中最后一项。

## Breaking Changes / 不兼容变更

None / 无。No database migration, no public API change. On Codex with a non-OpenAI model, MCP and multi-agent tools are not offered to that model; other clients and the `/v1` entry are unaffected. / 无数据库迁移、无公共 API 变更。Codex 使用非 OpenAI 模型时不再向该模型提供 MCP 与多智能体工具；其它客户端与 `/v1` 入口不受影响。

## Local update / 本地更新

- Local Windows amd64 Beta installer, not a public release and not signed. Fully exit OmniProxy from the system tray, back up the data directory, then run the installer over the existing installation. Codex itself does not need to restart to pick up the gateway change, but restarting it reloads the model catalog. / 本版本为本地 Windows amd64 Beta 生产安装包，未公开发布、未签名。请先从托盘完全退出 OmniProxy，备份数据目录，再运行安装器覆盖现有安装。Codex 不需要为网关改动重启，但重启会重新加载模型目录。
- Application/frontend version: `2.3.1-beta.5`; Windows numeric resources: `2.3.1.0`; NSIS installer base version: `2.3.1`. / 应用／前端版本为 `2.3.1-beta.5`，Windows 数字资源版本为 `2.3.1.0`，NSIS 安装器基础版本为 `2.3.1`。
- Existing accounts, routes, statistics and client configuration are preserved; this release has no database migration. / 保留现有账号、路由、统计与客户端配置；本版本没有数据库迁移。

## Verification boundary / 验证边界

- `task verify` passed before packaging: all Go packages, frontend tests (154 files / 935 tests), format, lint, typecheck and the Windows production build. / 打包前 `task verify` 通过：Go 全包、前端 154 文件／935 项测试、格式、lint、类型检查与 Windows 生产构建。
- New coverage: Core asserts the Codex entry marks requests it hands to the protocol pipeline; the gateway end-to-end case sends a real Codex tool set (function plus namespace) and asserts only the function tool reaches River while the model and effort are still rewritten. / 新增覆盖：Core 断言 Codex 入口改走协议处理时打上来源标记；网关端到端用例发送真实 Codex 工具集（函数＋命名空间），断言只有函数工具到达 River，且模型与档位仍被改写。
- Real upstream check (read-only production database, real River key, isolated listener) with the real tool shape: `/codex/v1/responses` + `DeepSeek-V4.1-Flash-1017` returned 200 in 2733 ms non-streaming and 200 in 904 ms streaming, and the echoed request shows only `exec_command` in `tools`. / 真实链路验证（只读生产库、真实 River Key、隔离实例，使用真实工具形状）：`/codex/v1/responses` + `DeepSeek-V4.1-Flash-1017` 非流式 200／2733 ms、流式 200／904 ms，回显请求的 `tools` 只剩 `exec_command`。
- Known limitation: the transparent WebSocket handshake carries no body, so with "Codex WebSocket" enabled those models still rely on the client falling back to HTTP. / 已知限制：透明 WebSocket 握手没有正文，开启「Codex WebSocket」后这些模型仍依赖客户端回退 HTTP。
