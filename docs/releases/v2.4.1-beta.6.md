# OmniProxy v2.4.1-beta.6

## Fixes / 修复

- **Antigravity requests no longer show up as a run of “cancelled / usage not reported” while the upstream is still thinking.** The desktop client gives a response only 60 seconds to start arriving (its log says `net/http: timeout awaiting response headers`), while the subscription’s thinking models may take several minutes before Google sends the first chunk — and therefore the response headers. The gateway previously wrote nothing until the provider had upstream headers, so `copyStream`’s 3-second header grace never started. For Antigravity streaming requests the gateway now commits `200` and `text/event-stream` three seconds after admission, keeps the connection alive with a `: keep-alive` comment every 10 seconds, and hands over to the normal stream copy as soon as upstream headers arrive. / 「上游还在思考时，Antigravity 请求不再出现成串的『已取消／未报告』。」桌面端只给响应头 60 秒（生成端日志为 `net/http: timeout awaiting response headers`），而订阅的思考型模型可能先想几分钟，Google 才发出第一个分片，也就是才回响应头。网关此前在 provider 拿到上游响应头前不写任何字节，`copyStream` 的 3 秒宽限根本不会启动。现在 Antigravity 的流式请求在受理 3 秒后先提交 `200` 与 `text/event-stream`，每 10 秒发一条 `: keep-alive` 注释保活；上游响应头一到就交给原有的逐行复制，不重复写状态码。

## Notes / 说明

- Scope is intentionally narrow: only requests attributed to the Antigravity client receive the early headers. Every other client keeps the previous semantics, where a failure is returned with its real HTTP status code (401/429/5xx). / 范围有意收窄：只有归属 Antigravity 客户端的请求会提前收到响应头。其它客户端保持原有语义，失败仍以真实 HTTP 状态码（401／429／5xx）返回。
- After the response headers are committed for Antigravity, a later failure can only abort the connection instead of changing the status code. Account rotation still runs inside the gateway on the real result, and the desktop client retries the aborted stream. / Antigravity 的响应头提交之后，之后再失败只能中断连接，不能改状态码；账号轮换仍在网关内部按真实结果完成，桌面端会对中断的流自行重试。
- `request_cancelled` / 499 accounting is unchanged: a client that really disconnects is still recorded as cancelled. / `request_cancelled`／499 的记账语义不变：客户端真的断开时仍记为取消。
- This is not a regression of beta.1’s header fix: beta.1 covered silence *after* upstream headers arrived (thinking chunks the adapter drops), which still works. The new case is the wait *before* upstream headers arrive. Evidence from the live database: cancels sit at 59,996–60,012 ms, and 34 of 37 on 2026-11-20 had attempt `status_code=499`, i.e. no upstream response at all. / 这不是 beta.1 响应头修复的复发：beta.1 覆盖的是「上游已回响应头、正文静默」（适配器丢弃思考分片）的情形，那部分仍然有效；这次是「上游响应头到达之前」的等待。本机数据库证据：取消都卡在 59,996–60,012 ms，2026-11-20 的 37 条里有 34 条的尝试 `status_code=499`，即从未拿到上游响应。
- Also included since beta.5: explicit proxy-scheme confirmation and self-healing (beta.5), usage statistics that merge reasoning-level variants of the same model (beta.4), and re-authorizing the same Google/ChatGPT account updating the existing card (beta.3). / 同时包含 beta.5 的内容：显式代理协议首次使用前握手确认与自愈；beta.4 的内容：用量统计按模型家族合并推理档位变体；beta.3 的内容：重新授权同一 Google／ChatGPT 账号会更新原账号。
- No database migration and no configuration rewrite. / 无数据库迁移、不改写配置。
