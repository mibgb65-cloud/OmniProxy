# OmniProxy v2.4.0

本正式版汇总自 v2.3.0 以来的全部变更，包含此前仅在本机构建的 `v2.3.1-beta.1`–`beta.29`
共 29 个测试版本，不需要逐个安装中间版本。相对 v2.3.0 共 121 个提交，其中 12 项新增、
19 项修复，新增三家内置服务商与四个数据库迁移。

This stable release collects everything since v2.3.0, including the 29 local-only
`v2.3.1-beta.1`–`beta.29` test builds. Intermediate installs are not required. The range spans
121 commits: 12 features, 19 fixes, three new built-in providers and four database migrations.

## Features / 新功能

- **HowToFix built-in provider.** Add an API Key account and the gateway calls
  `GET /v1/models` for that account's catalogue; Chat Completions is forwarded natively and
  Responses／Messages are converted to Chat and re-encoded into the caller's protocol. Accounts
  show the prepaid USD balance from `GET /v1/dashboard/billing/subscription`, and managed clients
  pick the models up from the same catalogue.
- **新增 HowToFix 内置服务商。** 添加 API Key 账号后网关按该账号调用 `GET /v1/models`
  拉取目录；Chat Completions 原生透传，Responses／Messages 转换为 Chat 后按调用方协议回编码。
  账号显示 `GET /v1/dashboard/billing/subscription` 的预付美元余额，受管客户端从同一目录取模型。
- **WorkBuddy AI subscription provider.** Browser-authorization sign-in with tokens kept in the
  DPAPI-protected store. The catalogue comes from the account's own `/v3/config`; per-model
  context window, output limit, image input and reasoning efforts follow what upstream declares.
  Non-streaming Chat and Responses／Messages clients are served by aggregating the upstream stream
  inside the gateway. Credits show `Credits`, `Extra credits`, `Total credits` and, when present,
  `Prepaid credits`, as display-only values.
- **新增 WorkBuddy AI 订阅服务商。** 浏览器授权登录，令牌保存在 DPAPI 受保护存储。模型目录取自
  账号自己的 `/v3/config`，上下文容量、输出上限、图片输入与推理档位跟随上游声明；非流式 Chat
  与 Responses／Messages 由网关聚合上游流后再回编码。额度卡显示 `Credits`、`Extra credits`、
  `Total credits` 与（存在时的）`Prepaid credits`，仅做展示、不参与计价。
- **WorkBuddy China mainland provider.** `copilot.tencent.com` is a separate built-in subscription
  provider with its own client fingerprint and login platform. Claude models served by that build
  are forwarded to the native Anthropic `POST /v1/messages` endpoint when the client speaks
  Messages, so reasoning levels work there.
- **新增 WorkBuddy 国内版服务商。** `copilot.tencent.com` 作为独立内置订阅通道，使用自己的客户端
  指纹与登录平台。该版本提供的 Claude 模型在客户端使用 Messages 时转发到原生
  `POST /v1/messages`，推理档位才生效。
- **Google subscription image input.** Gemini models now declare `text` + `image` in the model
  catalogue, so Antigravity and every managed client publish `supportsImages: true` and stop
  blocking attachments. Chat requests accept inline images inside tool results: text goes into
  `functionResponse`, the image becomes an `inlineData` part in the same user turn.
- **Google 订阅支持图片输入。** 目录中给 Gemini 声明 `text` + `image`，Antigravity 与所有读取
  该目录的受管客户端发布 `supportsImages: true`，不再拦截附件；Chat 请求接受工具结果里的内联
  图片：文本进 `functionResponse`，图片成为同一 user turn 的 `inlineData` 部分。
- **Tool-result image backfill.** When a client strips tool-result images down to the
  `Showing binary file of type image/png` placeholder (Antigravity Enterprise Gateway mode does),
  accounts the tool call's `tool_call_id` arguments contain an absolute path, and the gateway
  re-reads that file — sniffed as PNG／JPEG／GIF／WebP, capped and base64-encoded — backfills it as
  `inlineData` for Gemini-family targets.
- **回填被客户端丢弃的工具结果图片。** 客户端把工具结果图片剥成
  `Showing binary file of type image/png` 占位文本时（Antigravity 的 Enterprise Gateway 模式如此），
  网关按同一 `tool_call_id` 参数里的绝对路径回读文件，嗅探 PNG／JPEG／GIF／WebP 后编码回填为
  `inlineData`，仅对 Gemini 族生效。
- **DuMate image capability.** The two published DuMate aliases now declare `text` + `image`;
  the gateway already forwarded `image_url` parts, only the declaration was missing.
- **DuMate 图片能力声明。** 两条已发布别名声明 `text` + `image`；网关本来就转发 `image_url`，
  缺的只是能力声明。
- **Quota-aware Google account selection.** If the stored quota snapshot says a window of the
  model's quota group is at 0% and its reset is still ahead, the account is skipped for that model
  and no request is sent. Groups follow the official names: `gemini-4-argon*` belongs to
  `Gemini 4 Argon`, `claude*`／`gpt*` to `Claude and GPT models`, the remaining `gemini*` to
  `Gemini Models`. Unclassifiable models, missing snapshots and untrusted snapshots are never
  pre-screened.
- **Google 订阅额度窗口参与选号。** 已发布的额度快照里，该模型所属分组任一窗口为 0% 且重置时间
  未到时，路由跳过该账号、根本不发送请求。分组按官方名称：`gemini-4-argon*` 属
  `Gemini 4 Argon`，`claude*`／`gpt*` 属 `Claude and GPT models`，其余 `gemini*` 属
  `Gemini Models`。无法归类、缺快照与不可信快照都不预筛。
- **Google accounts page grouped by quota group set.** Accounts reporting the same set of group
  names sit together, and an account reporting an extra group such as `Gemini 4 Argon` forms its
  own section placed first. Grouping is keyed by the sorted name set, so a different upstream order
  never splits one set into two sections.
- **Google 账号页按额度分组集合分区。** 上报同一组名称的账号放在一起，多出 `Gemini 4 Argon`
  这类分组的账号自成一区并排在前面。分区以排序后的名称集合为键，上游顺序变化不会把一个集合
  拆成两区。
- **Readable plan badges.** Raw backend identifiers become tier names — `g1-ultra-tier` → **Ultra**,
  `g1-pro-tier` → **Pro**, `g1-free-tier`／`free-tier` → **Free** — Google AI Ultra 5x and 20x get
  distinguishable badges, and an identity that no longer returns a plan reads "No plan" instead of
  the misleading "Unknown plan".
- **套餐徽章可读化。** 原始后端标识映射为档位名——`g1-ultra-tier` → **Ultra**、`g1-pro-tier` →
  **Pro**、`g1-free-tier`／`free-tier` → **Free**；Google AI Ultra 5x 与 20x 使用可区分的徽章；
  身份不再返回套餐时显示「无套餐」，而不是容易误解的「套餐未知」。
- **Quota page: new providers' balances and local usage on one card.** HowToFix leaves "not
  supported yet" and shows the prepaid USD remaining amount with the same refresh, batch refresh
  and retained-snapshot behaviour as other balance providers; DuMate shows points. Both cards also
  show the locally recorded token usage. Points and tokens are never converted into each other, and
  a missing amount reads "Data unconfirmed" rather than "Exhausted".
- **配额页：新服务商余额与本机用量同卡。** HowToFix 不再显示「暂不支持」，改为显示预付美元余额，
  刷新、批量刷新与快照保留行为与其它余额服务商一致；DuMate 显示积分。两张卡都附带本机记录的
  Token 用量。积分与 Token 用量互不换算，数据缺失显示「数据待确认」而不是「已耗尽」。
- **Dashboard "Token share by model" and usage page "Yearly activity".** The dashboard gains a
  model-share card that follows the selected range; the usage page gains a 365-day heatmap with
  53 Monday-first columns, per-day hover detail and a Token／requests toggle.
- **首页「模型 Token 占比」与用量页「年度活跃度」。** 首页新增跟随所选时间范围的模型占比卡；
  用量页新增 365 天热图，53 列、周一开头，支持单日悬停详情与 Token／请求数切换。

## Bug Fixes / 问题修复

- **Streaming responses now send headers before the first token.** When the upstream stays silent
  for more than 3 seconds the gateway commits `200` with `text/event-stream` and keeps the
  connection alive with an SSE comment every 10 seconds. Previously nothing was written until the
  first token, so clients with a 60-second response-header timeout reported a reasoning turn as
  "cancelled" — one Antigravity task showed up as six such rows. Keep-alives are skipped while an
  SSE event is still being assembled.
- **流式响应改为在首个 token 前下发响应头。** 上游静默超过 3 秒即提交 `200` 与
  `text/event-stream`，之后每 10 秒发一条 SSE 注释保活。此前首个 token 前不写任何字节，有 60 秒
  响应头超时的客户端会把一次推理任务记成「已取消」——Antigravity 的一次任务曾变成 6 条这样的
  记录。正在拼装 SSE 事件时不做心跳，避免注释行把事件截断。
- **Codex with a non-OpenAI model no longer fails with 401.** The transparent proxy on `/codex/v1`
  shared only the OpenAI Responses contract and fell back to `api.openai.com` when the provider
  base URL was empty, sending third-party keys to the wrong host. `/v1/responses` (including
  `/responses/compact`) now reads the model and hands the request back to the protocol entry when
  the target is not an OpenAI provider.
- **修复 Codex 选非 OpenAI 模型整池 401。** `/codex/v1` 透明转发只与 OpenAI 共用 Responses 契约，
  提供商基址为空时一律回落 `api.openai.com`，第三方 Key 被发到错误主机。现在
  `/v1/responses`（含 `/responses/compact`）解析模型后，目标不是 OpenAI 就交回协议入口处理。
- **Codex namespace tool groups.** After routing to a third-party provider the request was still
  rejected locally with `400 unsupported_content` because it carried `type: "namespace"` groups
  that such providers cannot express. Those groups are dropped after routing; every function tool
  and every other field is preserved.
- **修复 Codex 命名空间工具分组。** 路由到第三方服务商后仍被本地 `400 unsupported_content`
  拒绝，因为请求带着对方无法表达的 `type: "namespace"` 分组。现在路由后移除这些分组，函数工具与
  其它字段全部保留。
- **SSE failure classification.** An upstream-reported error inside the stream is now recorded as
  `upstream_error_event`, while malformed JSON or a non-object shape stays
  `upstream_stream_failed`; a stream that ends before a terminal event is recorded as
  `upstream_stream_kind=incomplete_stream`.
- **区分上游 SSE 错误事件与流中断。** 上游在流里主动报错记为 `upstream_error_event`，非法 JSON
  或非对象形状仍为 `upstream_stream_failed`；在终结事件前结束的流记为
  `upstream_stream_kind=incomplete_stream`。
- **Orphan tool results and `response.incomplete`.** Codex Desktop injects its Companion Page
  snapshot as a `function_call_output` without a `call_id`; River answered `200` and then dropped
  the connection, surfacing as `error decoding response body`. The Codex entry now removes those
  orphan results, and the River adapter rejects the same shape with an explicit `400` outside the
  Codex entry. A response that ends because it hit `max_output_tokens` or a content filter is
  delivered as the terminal `response.incomplete` event instead of being treated as a truncation.
- **修复孤儿工具结果与 `response.incomplete`。** Codex 桌面端把 Companion Page 快照注入成没有
  `call_id` 的 `function_call_output`，River 先返回 `200` 再断开连接，客户端只看到
  `error decoding response body`。Codex 入口现在移除这类孤儿结果，非 Codex 入口由 River 适配器
  明确返回 `400`。命中输出上限或内容过滤的响应按终结事件 `response.incomplete` 交付，不再当作截断。
- **Codex 0.169 `include` values.** The new core requests `output.encrypted_content` by default;
  River drops the connection right after `200` when it receives it. The Codex entry removes that
  value and keeps `reasoning.encrypted_content`.
- **修复 Codex 0.169 的 `include` 取值。** 新内核默认请求 `output.encrypted_content`，River
  收到后会在 `200` 之后立刻断开。Codex 入口移除该取值，保留 `reasoning.encrypted_content`。
- **Inline images are validated by form, not by remote-URL size.** Codex returns a `view_image`
  result as roughly 1 MB of inline `data:image/png;base64,…`, but the River adapter applied its
  8 KiB remote-URL bound to every image address. Inline `data:image` is now allowed up to the
  component-wide 16 MiB; remote addresses keep 8 KiB. Empty addresses, non-image data URLs,
  oversized payloads and unknown structures are still rejected with `400`.
- **内联图片按形式校验，不再套用远程 URL 上限。** Codex 把 `view_image` 结果作为约 1 MB 的内联
  `data:image/png;base64,…` 返回，而 River 适配器把 8 KiB 的远程地址上限套到了所有图片地址。
  现在内联 `data:image` 放宽到组件统一的 16 MiB，远程地址保持 8 KiB；空地址、非图片 data URL、
  超限与未知结构仍返回 `400`。
- **Long Codex conversations.** The Responses validators still capped the `input` array at 512
  items; a thread that had reached 514 failed with `400 unsupported_content`. The bound is now
  100,000 items, matching the Messages path — the real boundary remains the 16 MiB request body.
  `custom_tool_call`／`custom_tool_call_output` history (Codex `apply_patch`) is accepted.
- **修复长 Codex 会话的输入条数上限。** Responses 校验仍把 `input` 数组限制在 512 条，已有 514 条
  的线程因此 `400 unsupported_content`。上限改为 100,000 条，与 Messages 路径一致，真实边界仍是
  16 MiB 请求体；同时放行 `custom_tool_call`／`custom_tool_call_output` 历史（Codex `apply_patch`）。
- **WorkBuddy AI: account could not be saved after a successful browser sign-in.** The new
  account's `INSERT INTO accounts` declared 11 columns but supplied 12 values, which SQLite
  rejected; the account layer had no stable code, so the UI collapsed to one generic message.
  Failures now carry `save_failed`／`configuration_changed` and the sign-in stages are logged.
- **修复 WorkBuddy AI 登录成功后账号无法保存。** 新建账号的 `INSERT INTO accounts` 声明 11 列却
  给了 12 个值，SQLite 直接拒绝；账号层没有稳定码，界面只显示一句通用提示。现在保存失败返回
  `save_failed`／`configuration_changed`，登录取证阶段也写入日志。
- **WorkBuddy AI: Credits could not be read.** The billing endpoint is not shaped like the chat
  API: it wants `POST /billing/meter/get-user-resource-summary` with an empty JSON body and the
  short `WorkBuddy/<version>` user agent. OmniProxy sent `GET` and was answered with a gateway
  `404`. The plan name now comes from the billing API's `SubscriptionPackageName`, and the UI
  recognises the stable code across the `workbuddy_ai:`／`subscription:`／`gateway:` prefixes.
- **修复 WorkBuddy AI Credits 读不出来。** 计费接口与对话接口形态不同：需要
  `POST /billing/meter/get-user-resource-summary`、空 JSON 正文与短 `WorkBuddy/<version>`
  UA，而 OmniProxy 发的是 `GET`，被网关回 `404`。套餐名改为取自计费接口的
  `SubscriptionPackageName`，界面也能识别 `workbuddy_ai:`／`subscription:`／`gateway:`
  三种前缀下的稳定错误码。
- **WorkBuddy AI: "Sync official models" always failed while background sync worked.** The manual
  sync path built its catalogue service in the Wails layer and only attached the Google
  subscription, so the WorkBuddy branch returned `unavailable` immediately. Both paths now share
  one wiring helper, and sync failures record the underlying code for the log.
- **修复 WorkBuddy AI 手动同步模型永远失败。** 手动同步在 Wails 层自建目录服务、只接了 Google
  订阅，WorkBuddy 分支直接返回 `unavailable`，而后台同步其实已写入 25 条模型。现在两条路径共用
  同一接线函数，失败时底层稳定码写入日志。
- **WorkBuddy AI: chat rejected with `11128`.** The upstream requires the first message to be a
  `system` message and OmniProxy forwarded client bodies as-is. The adapter now normalises
  `developer` → `system` and `max_completion_tokens` → `max_tokens`, prepends a default system
  prompt when the first message is not one, and retries once by moving the system prompt into the
  first user message if the upstream still refuses.
- **修复 WorkBuddy AI 对话被 `11128` 拒绝。** 上游要求首条消息是 `system`，而网关原样转发客户端
  正文。适配器现在归一 `developer` → `system`、`max_completion_tokens` → `max_tokens`，首条不是
  system 时补默认系统提示词，若上游仍拒绝则把系统提示词下移进首条用户消息重试一次。
- **WorkBuddy reasoning levels for `onlyReasoning` models.** `/v3/config` gives `max-model`,
  `gemini-4-carbon`, `gemini-4-argon` and `kimi-k3` only a `reasoning.effort` value instead of an
  effort list, so those models exposed no selectable levels; they now do.
- **补齐 WorkBuddy 只给 effort 的模型推理档位。** `/v3/config` 只给 `max-model`、
  `gemini-4-carbon`、`gemini-4-argon`、`kimi-k3` 一个 `reasoning.effort` 值而非档位数组，
  这些模型此前没有可选档位，现在补齐。
- **HowToFix: catalogue sync had no entry point.** The provider existed in the backend, but the
  Routing page's "sync official models" account list did not include the `howtofix` kind and no
  background starter existed. Sync now runs at startup and after account create/update/delete,
  provider enable/disable and a successful manual sync; the Routing page can force a refresh, and
  the merged sync status reports OpenAI and HowToFix jobs together.
- **修复 HowToFix 目录同步没有入口。** 服务商已在后端实现，但路由页「同步官方模型」的账号列表
  不含 `howtofix`，后台也没有同步启动器。现在启动与账号新增／更新／删除、服务商启用／停用、
  手动同步成功后都会自动补齐，路由页可强制刷新，同步状态与 OpenAI 任务合并展示。
- **Managed-client catalogues that stop updating now say why.** When another tool changes a
  client's config file, OmniProxy deliberately stops rewriting it, but the only trace was a
  `refresh_failed` log line. Each client's failure code now appears on its card, the list page
  summarises "N clients' configuration files were modified by another tool, catalogue
  auto-refresh is paused", and the primary action becomes "Re-read and apply" — one click that
  loads the current file, previews it and applies it without discarding the user's edits.
- **受管客户端目录停更不再静默。** 其它工具改写配置文件后网关按策略停止覆盖，但此前只在日志记
  `refresh_failed`。现在每个客户端的失败码显示在卡片上，列表页汇总「N 个客户端的配置文件已被
  其他工具修改，模型目录暂停自动更新」，主按钮变为「重新读取并应用」——一次点击读回当前文件、
  预览并应用，不丢弃用户改动。
- **Google prompt-cache tokens are recorded.** The Chat conversion read only prompt, candidate,
  thinking and total counts, so `usageMetadata.cachedContentTokenCount` never reached the request
  record.
- **记录 Google 订阅的缓存命中 Token。** Chat 转换只读了 prompt、candidate、thinking 与 total，
  `usageMetadata.cachedContentTokenCount` 从未进入请求记录。
- **Account-level refusals keep their real code and switch accounts.** WorkBuddy business refusals
  (`11158` model entitlement, `11128` channel, `11159` signature, `10085` fingerprint) now reach
  the gateway as stable codes instead of collapsing into one generic error.
- **账号级拒绝保留真实错误码并换号。** WorkBuddy 的业务拒绝（`11158` 模型无权限、`11128` 渠道、
  `11159` 签名、`10085` 指纹）以稳定码到达网关，不再塌成一条通用错误。
- **Family name plus effort resolves before provider selection.** The Antigravity desktop sends
  `gemini-4-carbon` with `reasoning_effort=high`, while only the WorkBuddy relay published that
  name — Google's own request was intercepted by the wrong provider. Resolution now happens before
  selection.
- **家族名加档位在选服务商前解析。** Antigravity 桌面端发 `gemini-4-carbon` 配
  `reasoning_effort=high`，而当时只有 WorkBuddy 中继发布这个名字，Google 自己的请求被错误服务商
  截走。现在在选服务商之前完成解析。
- **A 429 from a Google subscription is an account-level rejection.** A 429 without the official
  "quota will reset after …" text was classified as `rate_limited`, while the failover policy
  deliberately ignores every Google 429 (that rule exists for API Key accounts, whose keys share
  one project quota). The account was therefore never cooled and never switched. The gateway now
  switches to the next account in the same pool within the same request and cools that
  (account, model) until the reset time known from the snapshot — 60 seconds when neither the
  upstream nor the snapshot says when — and refreshes that account's snapshot once in the
  background, at most once per minute. API Key accounts keep the old behaviour.
- **Google 订阅的 429 改为账号级拒绝。** 没有官方「quota will reset after …」正文的 429 以前只归成
  `rate_limited`，而故障切换策略刻意忽略所有 Google 429（这条规则是给共享同一项目额度的 API Key
  账号用的），账号既不冷却也不换号。现在同一请求内换到同池下一个账号，并把该（账号，模型）冷却到
  快照里已知的重置时间——上游与快照都没给时按 60 秒——同时在后台刷新该账号快照，每账号每分钟
  至多一次。API Key 账号保持原行为。

## Breaking Changes / 不兼容变更

- No intentional public API, configuration-format or stored-semantics breaking change. Existing
  accounts, credential references, routes, statistics, data location and update preferences are
  retained; the 29 beta release notes all record `None`.
- 无主动改变公共 API、配置格式或存储语义的不兼容变更；既有账号、凭据引用、路由、统计数据位置与
  更新偏好全部保留；29 个 Beta 版本说明的不兼容变更均为「无」。
- Database migrations **049–052** are additive only: three `providers` rows (HowToFix,
  WorkBuddy AI, WorkBuddy China mainland) and one new `workbuddy_quota_snapshots` table. There is
  no `ALTER`, `DROP`, `UPDATE` or `DELETE`. Migrations already applied by a local Beta are not
  repeated.

- **Do not downgrade and let an older application write to the upgraded database.** Retain current

  rollback.
- **不要直接降级并让旧程序继续写入升级后的同一数据库。** 需要回退时，应保留当前数据，使用升级前

## Upgrade notes / 升级说明

1. Fully quit from the system tray and take a consistent data-directory backup including SQLite
   WAL; copying only a running database file is insufficient.
2. Download `OmniProxy-Setup-v2.4.0-windows-amd64.exe`, verify its `.sha256`, and install over the
   existing installation. Installation identity and data location are retained.
3. Local `v2.3.1-beta.*` users can upgrade directly, and both the stable and beta channels can
   discover this release. Externally modified client catalogues still require preview and explicit
   application.
4. GitHub Actions builds and project-self-signs the public installer, verifying its signature,
   certificate pin and SHA256. **Self-signing does not imply public CA trust or SmartScreen
   reputation.**

**中文升级步骤：**

1. 从托盘完全退出 OmniProxy，先备份当前数据目录；SQLite 备份须包含 WAL，不要仅复制运行中的
   主数据库文件。
2. 下载 `OmniProxy-Setup-v2.4.0-windows-amd64.exe`，核对同名 `.sha256` 后覆盖安装。
   安装身份与既有数据位置沿用原配置。
3. 本地 `v2.3.1-beta.*` 用户可直接升级，正式版与 Beta 渠道都能发现本版。客户端目录被外部修改时

4. 公开安装器由 GitHub Actions 构建，使用项目证书自签并校验签名、证书 pin 与 SHA256。
   **项目自签不等于公开 CA 信任或 SmartScreen 信誉保证**，Windows 仍可能显示未知发布者提示。

## Known limitations / 已知边界

- WorkBuddy AI and WorkBuddy China mainland coverage is contract-level only: real-account browser
  sign-in, the real `/v3/config` catalogues and real completions were not exercised through the
  app. The client fingerprints are pinned to upstream `5.9.3` / CLI `2.165.0`; a vendor release
  that changes them needs a corresponding update.
- WorkBuddy AI 与国内版的覆盖只到契约层：真实账号浏览器登录、真实 `/v3/config` 目录与真实对话
  未通过应用验证。客户端指纹固定为上游 `5.9.3` / CLI `2.165.0`，上游变更时需要同步调整。
- The Google quota-aware selection and 429 failover were locked by gateway tests driving two
  same-pool accounts through a real gateway port, but were **not observed against a live exhausted
  account**. The first request that reaches an account whose snapshot is still empty may still get
  one 429; it now fails over within the same request instead of surfacing the error.
- Google 额度窗口选号与 429 换号由网关测试锁定（两个同池账号走真实网关端口），但**没有在真实
  耗尽的账号上观察过**。某个账号还没有额度快照时，第一个打到它的请求仍可能吃到一次 429；
  现在它会在同一请求内换号，而不是把错误抛给客户端。
- DuMate context and output capacity are still not published because the upstream limits were not
  verified with a real request. HowToFix Anthropic／Gemini routes, long-context and tool behaviour
  beyond the tested contract were not verified.
- DuMate 的上下文与输出容量仍未公布，因为未用真实请求验证上游上限。HowToFix 的
  Anthropic／Gemini 路由、长上下文与工具行为超出已测契约的部分未验证。
- Historical request rows keep `—` for cached tokens because the count was discarded at write time
  and cannot be backfilled.
- 历史请求记录的缓存 Token 显示 `—`，因为写入时就丢掉了该计数，无法回填。
- Automated tests, builds and signature verification do not replace a real over-install,
  first-run migration or native-window acceptance. Publishing does not install, start the app or
  touch real accounts.
- 自动化测试、构建和签名校验不等于真实覆盖安装、数据库首次迁移或原生窗口验收。发布过程不会自动
  安装、启动应用或操作真实账号。
