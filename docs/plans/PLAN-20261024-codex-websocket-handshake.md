实施调整：假授权 factor-20 冷解密实测约 1.91 秒，单候选由初始建议 2 秒调整为
3 秒，仍受全部凭据合计 5 秒与握手总计 10 秒约束。隔离登录只在必要时交由官方组件
续期并持久化，避免自行旋转 refresh token 却只缓存访问令牌；网关自管授权继续自行续期。

目标：Codex CLI 和 Desktop 保持原生 WebSocket 选择行为，由 OmniProxy 的「Codex WebSocket」开关控制网关是否接受连接；修复握手前准备过慢、取消语义丢失和诊断信息不足的问题，不以关闭客户端 WebSocket 规避故障。

**成功不是“不再显示任何重连”，而是健康条件下首连可用，异常条件下按时退出、原因准确、资源可释放。**客户端是否重试及何时回退 HTTP，由客户端自身决定，网关不能对此作绝对承诺。

## 2. 排查依据与证据边界

### 2.1 已确认的现场行为

以下来自本次只读排查快照，不是持续监控结果：

| 证据               | 结果                                                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 网关持久化开关     | `websocket_enabled = 1`，不是界面与数据库开关不一致                                                                               |
| 截图中的 i18n 会话 | 19:21:30 连接本机 `/codex/v1/responses`，约 15 秒后超时；重试至 5/5，19:23:06 回退 HTTP                                           |
| 同时段网关日志     | 多次 `credential_unavailable`；相邻时段还有 `configuration_unavailable`                                                           |
| 当时账号类型       | 两个启用的 OpenAI 账号均为 `subscription_login`，不能只优化 `codex_auth_json` 路径                                                |
| 同时段订阅操作     | 额度查询出现 `stage=queue / quota_busy`，存在准备队列竞争的现场信号                                                               |
| 本机客户端版本     | CLI `0.163.0`，Desktop 内置核心 `0.164.0-alpha.11.1`；两者旧 `responses_websockets`／`responses_websockets_v2` 标记均为 `removed` |

客户端日志证明这批连接在等待建连时超时，但当前网关没有可关联的阶段耗时，**尚不能把等待时间唯一归因于锁排队、官方组件初始化、授权刷新、解密或上游拨号中的某一步**。禁止直接把这批 503 当成“账号登录全部失效”。

### 2.2 代码中已确认的问题

1. [透明 WebSocket 入口](../../internal/core/proxy/passthrough_socket.go)先完成 `OpenPassthrough`、取号／借凭据和上游拨号，再执行 `websocket.Accept`；所有准备时间都计入客户端的握手等待。
2. [订阅凭据准备](../../internal/application/subscription/token.go)使用服务级 `operations` 锁，随后打开官方组件并执行 `Account(ctx, true)`；[额度查询](../../internal/application/subscription/quota.go)也使用该锁。
3. [取号会话](../../internal/application/gateway/passthrough_session.go)将所有 `passthroughAttempt` 错误折叠成 `credentialFailed`；请求取消也可能被当作凭据失效，下一候选的配置读取又可能将已取消上下文映射成 `configuration_unavailable`。
4. [隔离授权续期](../../internal/infrastructure/codex/token_refresh.go)使用 `context.Background()`，OAuth 客户端自身期限为 30 秒；外层握手取消不能及时中断这一步。
5. [客户端配置写入器](../../internal/application/agentconfig/patch.go)仍写旧 WebSocket `false` 标记；它们在上述版本已移除，不能作为真实传输控制手段。
6. 透明 WebSocket 路径未创建普通 HTTP 的请求记录，现有错误日志也缺少阶段与耗时；请求列表中的 HTTP 200 不能证明之前的 WebSocket 成功。

### 2.3 已有验证的局限

只读排查时，代理核心、网关、订阅服务相关定向测试通过；已有用例主要使用快速成功／失败的假凭据。
这不能证明“真实凭据准备较慢时仍能在客户端期限内握手”，也不能替代两个真实客户端的端到端验收。

## 3. 约束与方案选择

### 3.1 必须保持的边界

- 保留 `/codex/v1`、固定前缀鉴权、Host／Origin／loopback 校验、并发上限及同池账号约束。
- 保留真实上游 WebSocket 双向透明中继，不改回 WebSocket 转 HTTP/SSE 的协议复刻。
- 同时支持 `subscription_login` 和 `codex_auth_json`，不要求用户重新授权或强制迁移登录材料。
- 保留账号成员、工作区、授权配置及路由版本校验；同一工作区不等于同一成员。
- 不改 Codex 的提供商身份、会话、模型、推理档位、登录文件或用户自定义接入方式。
- 开关仍只控制接收与后续客户端帧，不承诺立即触发客户端 HTTP 回退，也不新增自动协议转换。
- 不在日志、前端、普通 SQLite 或测试输出中写入令牌、授权头、提示词、完整认证文件或带凭据 URL。
- Core 不依赖 Wails／React；不增加大依赖，不扩大为通用代理重构。

相关决策：[ADR-005](../decisions/ADR-005-preserve-agent-session-identity.md)、[ADR-020](../decisions/ADR-020-protected-codex-auth-cache.md)、[ADR-021](../decisions/ADR-021-fixed-agent-entry-prefixes.md)、[ADR-023](../decisions/ADR-023-codex-v1-transparent-passthrough.md)、[ADR-024](../decisions/ADR-024-gateway-owned-codex-login.md)。冲突处以已接受的后续决策及本次用户明确要求为准。

### 3.2 方案比较

| 方案                                       | 好处                                   | 问题与决定                                                     |
| ------------------------------------------ | -------------------------------------- | -------------------------------------------------------------- |
| 关闭客户端 WebSocket或延长客户端等待       | 表面上可能减少超时                     | 不符合目标，且旧标记已移除；不采用                             |
| 先向客户端返回 101，再慢慢准备上游         | 能更早结束握手                         | 将错误推迟为连接内失败，丢失握手状态和安全换号窗口；本轮不采用 |
| 保持上游先连，优化准备快路径并限制总预算   | 保留真实错误与握手前换号，修改范围可控 | 推荐；异常时仍可能由客户端重试，必须明确这一边界               |
| 新建连接池、常驻官方子进程或大规模预热系统 | 可能进一步降低冷启动成本               | 生命周期及授权隔离成本高；先测量，本轮不作为前提               |

## 4. 分阶段实施

### 阶段 A：先补诊断与取消语义（P0）

**修改范围：**代理握手入口、取号会话、凭据准备与续期；复用中心日志脱敏设施。

1. 为一次握手生成独立关联 ID，贯穿 `selection`、`credential_queue`、`credential_prepare`、`upstream_dial`、`downstream_accept` 和结束事件；账号尝试仅记录序号，不记录敏感身份。
2. 记录阶段耗时、总耗时、稳定结果码和可证实的状态码；禁止输出底层错误全文或认证相关 URL。
3. `Next` 进入候选和收到准备错误时先检查请求取消／总期限；请求已结束时立即停止遍历，不再访问下一账号、不施加凭据失效冷却。
4. 区分客户端取消、网关握手预算耗尽、单候选准备超时、真实凭据不可用、配置读取失败与上游握手拒绝；优先沿用已有稳定码，确需新增时同步契约与测试，不虚构已存在的错误码。
5. 将请求上下文传入 `UseFreshToken`、OAuth 请求及所有可取消等待，更新真实调用者与假实现；不得只修改函数签名而保留内部 `context.Background()`。
6. 对暂时无法中断的本地 KDF 明确边界：调用前后检查取消、保留有界并发；不得为“及时返回”启动不受管理的后台解密或泄露结果。
7. 每条退出路径释放并发槽、健康租约、官方子进程和两端连接，清理临时凭据；已取消请求不再尝试向断开的客户端补写“503”来冒充有效交付。

**阶段验收：**能够分辨“等锁被取消”与“凭据实际失效”；取消后不轮换、不启动新的 OAuth／拨号，不遗留资源；日志能关联到一个握手的各阶段。

### 阶段 B：建立端到端握手预算（P0）

1. 给整个握手准备设立统一总预算，覆盖取号、排队、凭据、全部候选拨号及确认握手；不能给每个候选重新分配一份完整预算。
2. **初始工程建议：总预算 10 秒，全部凭据准备合计最多 5 秒，单候选准备最多 2 秒；拨号仅使用剩余预算，最多 5 秒。**这些值是待验证的内部默认值，不是既有产品要求，也不代表所有 Codex 版本都有固定 15 秒期限。
3. 子阶段预算取父上下文剩余时间与阶段上限中的较小值；数据库读取、调度和失败处理同样消耗总预算，禁止因预算相加而超过总期限。
4. 单账号准备到期只有在父请求仍有效、还有时间且允许同池切换时才尝试下一候选；不将一次慢准备永久标为授权失效。
5. 保持现有最多三次上游尝试、固定账号和故障切换规则；预算耗尽及时结束，不通过无限重试／sleep 延长握手。
6. `websocket.Accept` 前再次检查开关和请求是否仍有效，覆盖“准备过程中关闭开关”的窗口；不只依赖握手开始与第一帧的检查。
7. 握手成功后释放握手预算的计时资源，中继改用连接／请求生命周期上下文；**不能让 10 秒握手期限变成正常长连接的寿命**。

**阶段验收：**模拟慢上游时，在配置预算内结束并给出准确类别；健康长连接超过握手期限仍可继续多轮收发。

### 阶段 C：缩短凭据热路径，避免跨账号队头阻塞（P1）

#### C1. 先处理现场使用的 `subscription_login`

1. 测量阶段 A 的数据，确认强制授权刷新、组件启动、解密和排队各自的耗时，保留冷／热两种结果。
2. 将“借出仍有效的授权”与“调用官方组件刷新授权”分开。避免每次握手都无条件 `Account(ctx, true)`，但**不能直接删除现有 `sameEmail`／工作区／账号版本校验**。
3. 优先复用已有受保护授权快照及续期机制。快路径必须核对受控 profile、成员身份、官方账号标识、授权版本、有效期及当前启用状态；无法证明身份一致时不得借出令牌，进入有界官方校验或明确失败。
4. 仅在必要时启动官方组件／续期；授权文件变化、重新登录、账号停用／删除／注销和身份变化时，既有快照必须失效。
5. 不为本次性能优化新增长期明文令牌缓存，不降低官方解密强度；涉及 ADR-020 的保护范围变化时先评审并补充决策。

#### C2. 两种凭据来源统一取消与并发规则

1. 检查 `codex_auth_json` 的刷新、回写和失败回退，同样遵守父请求预算；已过期令牌不能伪装为可用，旋转后的 refresh token 不得被旧结果覆盖。
2. 审计所有使用 `operations` 的调用者，再将授权准备／刷新所需互斥收敛到账号身份作用域；同账号的读取、续期、替换与注销必须协调，不能只给 `prepareToken` 单独换锁。
3. 保留确有必要的全局登录交互互斥和昂贵 KDF 并发限制；不把“跨账号互不阻塞”理解成无限并发启动官方组件或解密。
4. 同一身份的并发刷新应合并为一次有界操作。若实施共享刷新，明确等待者取消、最后一个等待者退出、应用关闭及结果版本复核；不能让首个请求取消拖死其余等待者，也不能遗留无限期后台任务。
5. 共享操作必须在发布结果与写回凭据前再次核验身份／版本，防止重新授权后发布旧结果。

**阶段验收：**健康热路径不再无条件启动组件／强刷；慢账号不能耗尽其他独立账号的全部握手时间；同账号不发生并发刷新覆盖和身份串用。

### 阶段 D：清理客户端旧标记与文档契约（P1）

1. 内置 `openai` 接入不再写入已移除的两个 `false` 标记，也不改为强写 `true`；让客户端保持原生默认行为。
2. 对现有受管配置，仅在受管记录与修订校验能证明归属时移除 OmniProxy 写入的旧标记；保留用户自定义值、其他 feature、注释和备份／恢复语义。无法证明归属时保留并提示，不直接清理真实文件。
3. 自定义提供商的 `supports_websockets=false` 单独评估：不能对未知第三方上游盲目开启；只对明确路由到支持 WS 的 OmniProxy Codex 受管入口调整，其他配置保持兼容。
4. 更新接入／恢复测试，确认不写 `model_providers.openai` 覆盖表、不改变 auth.json、不强制更换提供商。
5. 更新 ADR-023 关于客户端 `false` 标记的旧结论，以及 `GATEWAY.md`／`LOCAL_AGENTS.md`／必要的架构与测试说明；明确开关允许／拒绝，不保证客户端立刻回退 HTTP。

### 阶段 E：补全最小连接可观测性（P1）

- 至少区分握手成功、准备失败、上游拒绝、策略关闭、客户端取消、上游断开和中继读写失败，记录可证实的方向与关闭码。
- 连接成功或正常关闭不等于每轮模型调用成功；不把 101 算成模型请求成功，不伪造 Token、模型或 HTTP 状态。
- 本轮不扩展为逐个 `response.create` 的计费／请求记录系统，不为展示连接失败新增迁移；利用阶段 A 的连接日志补齐诊断缺口。
- 当前透明路径仍保留“每个后续客户端帧前检查开关”，不扩大为无客户端帧时也必须立即主动断开的新产品承诺。

## 6. 回归测试矩阵

使用临时 SQLite、假授权和本地 `httptest` WebSocket／OAuth 服务，禁止默认访问真实账号或公网。通过可注入的小预算／时钟覆盖超时，避免每项测试固定等待 15～30 秒。

| 场景                                   | 必须断言                                                        |
| -------------------------------------- | --------------------------------------------------------------- |
| 健康账号首连、重复热连接               | 收到真实 101，文本／二进制帧双向一致，不额外强刷                |
| 准备锁被占用后客户端取消               | 及时退出；不访问下一账号、不冷却健康账号、无租约／槽泄漏        |
| 单候选慢、下一候选健康                 | 在总预算内安全换号；固定账号时不越权换号                        |
| 多个候选均慢                           | 总耗时不随候选数线性叠加超过总预算                              |
| OAuth／上游握手阻塞                    | 父取消传播至 HTTP 请求；不会再多等默认 30 秒                    |
| 单候选超时与父请求取消                 | 前者按策略决定是否换号；后者立即停止，日志类别不同              |
| A 账号额度刷新阻塞，B 账号建连         | B 不被无关账号的授权队列串行拖住；资源并发仍有上限              |
| 同账号并发借凭据／刷新                 | 刷新合并，等待者独立取消，旧续期结果不能覆盖新授权              |
| 同工作区不同成员、版本变更、注销       | 不串号，不复用失效快照，不发送旧身份请求                        |
| 建连前、准备中、已建连后关闭开关       | 前两者不确认新握手；后者不再转发新的客户端帧；HTTP/SSE 不受影响 |
| 连接持续时间超过握手预算               | 多轮收发仍正常，握手子上下文未错误约束中继寿命                  |
| 上游 401／429／5xx 和明确拒绝          | 保持真实握手结果、同池换号及不重放已发送业务帧                  |
| 配置首次接入、受管刷新、外部修改与恢复 | 不重写旧标记、不删用户值、不改变官方身份，恢复可逆              |
| 日志与错误输出                         | 关联 ID 可追踪，阶段／耗时可用；没有秘密、完整正文或带凭据 URL  |

新增测试名称以实施时实际命名为准，不将尚不存在的测试命令写成已通过。

## 7. 验证与实机验收

### 7.1 开发验证顺序

先执行已有定向用例与新增回归，再运行相关完整包；全部修改收敛后执行仓库单一质量门：

```powershell
go test ./internal/core/proxy ./internal/application/gateway ./internal/application/subscription ./internal/infrastructure/codex ./internal/application/agentconfig -count=1
task verify
```

这些命令属于**后续实施计划**，不代表本次编写文档时已经运行。实现涉及前端或公开错误映射时，在质量门前增加对应定向前端测试。

### 7.2 性能与行为验收

1. 本地可控假上游、有效凭据热路径：连续 20 次握手全部成功，建议目标 P95 小于 2 秒；这是工程验收目标，不是公网性能保证。
2. 故障注入：超时／取消在配置总预算及合理调度容差内退出，取消后资源数量回到基线；长连接不受握手期限误伤。
3. 用户同意进行实机验证后，分别用 CLI 和 Desktop，以低成本请求验证冷启动、热连接、持续多轮、并行会话及开关切换；记录实际客户端／网关版本、关联 ID、阶段耗时和是否回退。
4. 实机健康场景首连成功，不再固定出现约 15 秒一轮的 1/5～5/5；若失败，日志可指出具体阶段。账号失效、上游不可用或用户关闭开关时，不要求“永远没有重连”。
5. 不用 HTTP 200 替代 WS 成功证据：必须有对应握手成功与真实帧往返记录；回退到 HTTP 应明确记为回退。
6. 若冷路径无法在预算内完成，保留明确失败与测量结果，再决定是否需要额外预热／组件复用及 ADR；不能偷偷放宽到客户端已经放弃的时间范围。

## 8. 交付顺序、风险与回退

建议按可独立验证的小改动推进：

1. 阶段诊断＋取消错误修正＋OAuth 上下文传递。
2. 统一握手预算＋慢握手回归＋握手前策略复核。
3. 凭据快路径＋跨账号协调优化＋身份／刷新竞争测试。
4. 旧标记清理＋连接可观测性收尾＋文档同步＋完整质量门＋实机验收。

主要风险：误判授权身份、刷新并发覆盖、共享操作取消传播错误、将握手期限带入中继、删除用户自定义配置。它们必须有负向测试，不能以“性能更快”为由降低校验。

回退以独立提交为边界，撤回本轮行为变更、保留有用诊断；不回滚用户账号数据库、不覆盖 auth.json、不强制关闭客户端 WebSocket。当前工作区有大量其他任务改动，实施前记录基线，任何提交与回退都不得夹带或丢弃这些内容。
